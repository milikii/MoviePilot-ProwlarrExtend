1. 先承认优点（否则不公平）

这套代码不是“烂项目”。它有明显的工程自觉：

纯函数抽取方向正确。mapping.py、selection.py、search_http.py、formats.py、quality.py、batching.py、linecheck.py、eta.py、language.py、codes.py 都是可独立测试的纯逻辑，这在 MoviePilot 插件里很少见。

字幕写盘是原子的：临时文件 + os.replace，失败不留半成品（translate_ops.py:59-65）。

翻译缓存设计认真：按阶段、模型、上下文、术语表、批次联合 key，缓存不写媒体库、不缓存 API Key（translate_ops.py:305-375）。

有取消、有状态持久化、有阶段耗时、有 failure_code。这些是可观测性的正确方向。

有版本契约测试：plugin_version 必须与 package.v2.json 一致（tests/test_contracts.py:109-112），这是个好习惯。

PT 场景细节考虑到位：freeleech 倍率、forced 字幕、只写外挂字幕不动 MKV、做种校验、keep_intermediate 清理。

文档量大：README、PLAN、MAINTENANCE、CLAUDE.md 都有，说明作者有长期维护的意图。

问题不在于“不会写代码”，而在于把聪明用在了错误的地基上。

2. P0：阻塞上线或直接产生错误结果的问题

P0-1　MoviePilot v3 上核心链路已断（三处独立硬断点）

这不是“未来风险”，是当前事实。插件写的是 MoviePilot v2.14.0（2026-06-30）的 API，本仓库最后提交是 2026-08-16；v3.0.0 于 2026-09-12 发布，v3.1.9 于 2026-10-22 发布。作者当时不可能预知 v3，但今天必须补这笔迁移债。

如果这是有意的产品边界，README 必须明确写“仅支持 v2.14.x，不支持 v3”，并在插件市场标注；否则 v3 用户安装后看到的是“已启用、有索引器列表、但搜不到任何东西”。这比直接报错更糟。

断点 A：SitesHelper.add_indexer 已不在 v3 的公开接口里

插件在 __sync_helper_indexers 中注册虚拟站点：

# plugins.v2/prowlarrextend/__init__.py:744
self.sites_helper.add_indexer(domain, copy.deepcopy(indexer))

而 v3 的公开类型声明 app/application/site/sites.pyi 中没有 add_indexer，整个 v3 源码也没有任何调用点。即使编译产物里还残留这个方法，它也已经不是契约；依赖它就是在赌下一次构建。

断点 B：Site 的 db=None 兼容层被移除

插件全程用 None 代替数据库会话：

# plugins.v2/prowlarrextend/__init__.py:785-808
site = Site.get_by_domain(None, domain)
Site(**payload).create(None)
site.update(None, update_payload)
Site.delete(None, legacy_site.id)

v2 的 @db_query / @db_update 装饰器会在 db=None 时自动开 session；v3 去掉了这层兼容：

# MoviePilot v3.1.9 app/db/models/site.py:66-70
def get_by_domain(cls, db: Session, domain: str) -> Optional[Self]:
    site = db.execute(select(cls).where(cls.domain == domain)).scalars().first()

db=None 时直接 AttributeError: 'NoneType' object has no attribute 'execute'。也就是说，即使 add_indexer 还在，同步也会在下一步崩掉。

断点 C：v3 的搜索链只给插件传 site={}，不再传真实站点

v3 把“插件资源源”和“站点索引器”拆成了两条路径：

# MoviePilot v3.1.9 app/chain/base.py:659-673
def search_plugin_torrents(self, keyword, mtype=None, page=0):
    return self._module_dispatcher.execute_plugin_modules(
        "search_torrents", None, site={}, keyword=keyword, mtype=mtype, page=page
    ) or []

def search_site_torrents(self, site, keyword, mtype=None, page=0):
    return self._module_dispatcher.execute_system_modules(
        "search_torrents", None, site=site, keyword=keyword, mtype=mtype, page=page
    ) or []

插件只会被 search_plugin_torrents 调用，site={}。

插件的 search_torrents 第一行就是 if not site: return []（__init__.py:502-503），所以永远返回空。

带 site 的那条路径只执行 system modules，插件的 get_module() 注册在 _plugin_catalog，不在 _module_catalog，永远收不到调用。

v2 不是这样。v2.14.0 的搜索入口仍然 self.search_torrents(site=site, ...)（app/chain/search.py:1815-1824），插件能收到 site。v3 把这条路径拆了，插件的核心机制随之失效。

失败时的表现很具有欺骗性

sync_indexers 在崩溃前已经做了两件事：

self._indexers = indexers                 # 索引器列表已就绪
self.__persist_indexer_metadata()         # catalog 已写回配置

然后才在 __sync_helper_indexers 或 __sync_site_records 崩溃。结果是：

插件详情页可能显示“已桥接 N 个索引器”；

表单里的多选列表有数据；

但 MoviePilot 搜索永远没有 Prowlarr 结果；

日志里只有线程异常或 cron 异常，普通用户很难把两者联系起来。

这比“安装即报错”更糟：它看起来是好的。

为什么测试没发现

因为测试把这三个契约全部替换成了自己写的替身：

# tests/conftest.py:87-97
_install_module("app.helper.sites", SitesHelper=type("SitesHelper", (), {
    "get_indexer": lambda self, domain: None,
    "add_indexer": lambda self, domain, value: None,   # ← 替身定义了真实宿主已删除的方法
}))

# tests/conftest.py:120
_install_module("app.db.models.site", Site=type("Site", (), {}))

# tests/test_prowlarrextend.py:162-181
class Site:
    @classmethod
    def get_by_domain(cls, _db, domain): ...   # ← 接受 None，和 v2 一样

测试不是验证“插件是否符合宿主”，而是验证“插件是否符合测试自己写的宿主”。 宿主 API 一漂移，测试全绿，线上全挂。这是这套测试最根本的问题。

修法方向：v3-first，把插件做成 plugin source；site={} 时扇出到全部桥接索引器；彻底删除 SitesHelper.add_indexer、Site CRUD、假域名、SystemConfigKey.IndexerSites 写入。具体见第 7 节。

P0-2　字幕解析器会静默丢条目

SRT_TIME 只接受“2 位小时 + 3 位毫秒”：

# plugins.v2/subtitlehunter/constants.py:31-34
SRT_TIME = re.compile(
    r"(?P<start>\d{2}:\d{2}:\d{2}[,.]\d{3})\s+-->\s+"
    r"(?P<end>\d{2}:\d{2}:\d{2}[,.]\d{3})(?P<tail>.*)"
)

parse_srt 对不匹配的块直接 continue，不计数、不告警：

# plugins.v2/subtitlehunter/formats.py:52-54
match = SRT_TIME.match(lines[0].strip())
if not match:
    continue

实测：

输入时间轴
解析结果

0:00:01,00 --> 0:00:02,00
0 条

00:00:01.5 --> 00:00:02.5
0 条

00:00:01,000 --> 00:00:02,000
1 条

现实里 0:00:01,00（1 位小时 + 2 位毫秒）和 00:00:01.5（1 位小数）并不罕见，尤其是老片、非英语字幕、手工转制的 SRT。结果：

整文件都是这种格式 → _translate_subtitle_file 返回“未解析到有效字幕条目”，任务失败；

文件里混合了标准与非标准块 → 只翻译能解析的部分，输出的中文字幕缺行，而 validate_translated_cues 只比较“解析后的 source”和“解析后的译文”，两边都缺同样的行，所以校验通过。

这是静默的数据损失，不是崩溃。 用户看到的是一条“翻译完成”的通知，播放时才发现中间少了几句。

修法：解析器接受 1–2 位小时、1–3 位毫秒、./, 分隔；统计 skipped_blocks；跳过比例超过阈值（例如 2%）时直接失败并给出样例；用黄金字幕集做回归。

P0-3　ASS / SRT 的样式与定位标签在翻译后全部丢失

翻译输入前会剥掉所有标签：

# plugins.v2/subtitlehunter/formats.py:12-16
def plain_subtitle_text(text: str) -> str:
    cleaned = re.sub(r"<[^>]+>", "", text or "")
    cleaned = re.sub(r"\{[^}]*}", "", cleaned)
    ...

ASS 的 {\an8}（顶部定位）、{\pos(...)}、{\i1}（斜体）、卡拉 OK 标签，以及 SRT 的 <i>，都在这一步被删除。翻译完成后，render_ass 把纯译文写回 Text 字段：

# plugins.v2/subtitlehunter/formats.py:117-123
fields[cue.ass_text_index] = (cue.text or "").replace("\n", "\\N")
lines[cue.line_index] = "Dialogue: " + ",".join(fields)

实测：

原文：  {\an8}Hello world
译文：  你好世界

{\an8} 没了。顶部提示（标识、歌词、屏幕文字）会掉到画面底部；斜体、颜色、定位全部失效。

对于“能看就行”的用户，这是小问题；对于 ASS 字幕，这是样式灾难。README 说“适合 Jellyfin/Emby/Plex 字幕播放”，但没有提样式丢失。

修法：在 SubtitleCue 上保存 style_prefix / style_suffix（或一个 tag mask），翻译只处理纯文本，渲染时把标签拼回去；SRT 的 <i> 同理。更彻底的做法是“掩码—翻译—还原”：把标签替换成 \u0000{n}\u0000 占位符，翻译后按占位符还原。

3. P1：正确性与可靠性问题

P1-1　FORCED_PATTERNS 把正常片名误判为 forced

# plugins.v2/subtitlehunter/constants.py:27-30
FORCED_PATTERNS = re.compile(
    r"(^|[._\-\s\[\]()])(forced|foreign|only|signs?)(?=$|[._\-\s\[\]()])|强制|特效",
    re.IGNORECASE,
)

only、signs、foreign 作为独立 token 出现在片名里时，会被当成 forced：

文件名
forced

The.Only.Living.Boy.2018.en.srt
True

Signs.2002.en.srt
True

Foreign.Correspondent.1940.en.srt
True

Only.The.Brave.2017.en.srt
True

movie.en.forced.srt
True（正确）

后果：

_select_english_source 把 forced 排除出翻译源，于是这些片子“找不到英文源”或被跳过；

_is_usable_external_chinese_track 也拒绝 forced，已有的中文字幕可能被当成不可用；

用户完全不知道为什么这两部片子不翻译。

修法：forced 只应匹配“语言标签之后的修饰词”，例如 \.(forced|foreign)\.(srt|ass|ssa)$；删除 only / signs；用一组真实片名做回归测试。

P1-2　中文覆盖率 50% 就能放行“半英文”译文

# plugins.v2/subtitlehunter/constants.py:37
CHINESE_COVERAGE_THRESHOLD = 0.5

has_chinese_cue_coverage 只统计“含中文或英文的行”，中文行占比 ≥ 50% 即通过。实测：

原文 4 条英文
译文 2 条中文 + 2 条英文
validate_translated_cues -> (True, "")

也就是说，模型只翻了一半，质量门放行。对于 1500 条的电影字幕，750 条英文留在中文字幕里，用户会看到中英混杂，而插件报告“完成”。

修法：
- 覆盖率阈值提到 0.9；
- 增加逐条检查：源文本超过 N 个拉丁词、译文却完全没有中文 → 记为失败；
- 区分“短感叹词/专有名词可保留英文”和“整句未翻译”；
- 质量门失败时保留已有缓存并明确报错，不要静默输出半成品。

P1-3　翻译重试是“有界地卡死”，且没有输出上限

# plugins.v2/subtitlehunter/translate_ops.py:270-303
attempts = self._api_retries + 1          # 默认 11 次
...
delay = min(300, max(1, 5 * (2 ** min(attempt, 6))))

默认 api_retries=10，单阶段最坏等待：

5 + 10 + 20 + 40 + 80 + 160 + 300 + 300 + 300 + 300 = 1515 秒 ≈ 25 分钟

quality 模式每批 3 个阶段（literal → reflect → polish），单批最坏 75 分钟。5 个并发批次里只要有一个模型持续 400/解析失败，整个任务就会卡很久。README 把“失败有界”写成优点，但这不是有界，这是有界地卡死。

更严重的是重试不区分错误类型：

401/403（Key 错）→ 重试 11 次；

400（context too long / temperature unsupported）→ 重试 11 次；

JSON 解析失败（模型输出被截断）→ 用同样的 prompt、同样的 batch 再试 11 次；

只有 429/5xx/超时才值得重试。

同时 _chat_completion 没有设置 max_tokens：

# plugins.v2/subtitlehunter/translate_ops.py:450-455
body = {
    "model": ai_config.get("model"),
    "messages": messages,
    "temperature": 0.2,
}

默认 60 条/9000 字符的批次，输出 JSON 很可能超过网关默认的 4k output cap，被截断 → 缺 index → 触发“缺少字幕索引”异常 → 重试同一个过大的请求 → 再次截断。这是一个自我强化的失败循环。

修法：
- 只对 429/5xx/超时/连接错误重试；4xx（除 429）立即失败；
- 尊重 Retry-After；指数退避加 jitter；单批总重试时间封顶（如 3 分钟）；
- 设置 max_tokens，按 token（而非字符）估算批次；
- 连续两次“缺 index / 输出截断”时，把批次二分递归重试，直到 1 条；这比重复同一个请求有效得多；
- 失败批次标记为失败并继续其他批次，输出“部分完成 + 明确失败列表”，不要阻塞整片。

P1-4　“复用系统智能助手”并没有真正复用

# plugins.v2/subtitlehunter/translate_ops.py:808-817
if self._model_source == "system":
    config = {
        "provider": getattr(settings, "LLM_PROVIDER", None) or "openai",
        "model": getattr(settings, "LLM_MODEL", None),
        "api_key": getattr(settings, "LLM_API_KEY", None),
        "base_url": getattr(settings, "LLM_BASE_URL", None),
        ...
    }

问题有两层：

读错了配置源。v3 的运行时配置通过 get_runtime_setting() / runtime provider 读取，settings 可能只是环境变量/默认值。用户在 UI 里改的智能助手模型、Key、Base URL，插件可能读不到。

只支持 OpenAI 兼容的 /chat/completions。系统智能助手可以是 Gemini 原生、Claude 原生、Azure OpenAI、Ollama 等，路径、鉴权、请求体都不同。_chat_completion 直接拼 {base_url}/chat/completions，对非 OpenAI 兼容 provider 必然失败。

README 说“默认复用 MoviePilot 系统智能助手配置”，这个承诺目前只在“系统助手恰好是 OpenAI 兼容 + 恰好写在 settings 里”时成立。

修法：抽一个 TranslationProvider 协议：
- SystemLLMProvider：走 MoviePilot 的 LLMHelper / get_runtime_setting，由宿主处理 provider 差异；
- OpenAICompatProvider：保留现有直连，用于自定义网关；
- MockProvider：测试用。

这样“系统助手”才是真的复用，而不是自己猜配置。

P1-5　非 UTF-8 字幕会被静默损坏

# plugins.v2/subtitlehunter/translate_ops.py:38
content = source_path.read_text(encoding="utf-8-sig", errors="ignore")

errors="ignore" 会把 GBK、CP1252、UTF-16 的字节直接丢掉。结果不是报错，而是“解析出一些乱码条目/空条目”，翻译质量崩坏，甚至 parse_srt 返回 0 条。

同样的问题出现在：

_subtitle_file_has_chinese_text（media_ops.py:26）

_estimate_scan_subtitle_chars（workflow.py:653）

修法：用 charset-normalizer / chardet 检测；按 utf-8-sig → utf-16 → gb18030 → cp1252 回退；全部失败时明确报错，不要 errors="ignore"。加一组 GBK/UTF-16 的黄金文件。

P1-6　季包入库只处理第一集

on_transfer_complete 对每个 transfer.complete 都尝试启动任务，而 _start_background_job 是“有任务就拒绝”：

# plugins.v2/subtitlehunter/runtime_ops.py:61-64
with self._status_lock:
    if self._job_active:
        logger.warning("已有字幕任务正在运行，跳过")
        return False
    self._job_active = True

季包（10 集）入库时，事件几乎同时到达：第 1 集启动，第 2–10 集全部被拒绝。如果用户没有配置定时任务，后面 9 集永远不会被处理。

修法：按目标目录做 debounce（30–60 秒），维护 pending 集合，合并成一个目录级任务；或者做一个队列，_job_active 只表示“消费者在跑”，新事件入队而不是丢弃。

P1-7　后台任务锁是进程内的，重载/多 worker 会双跑

_job_active 是实例属性，stop_service 只设置 cancel event，不 join 线程。插件热重载后：

旧线程可能还在跑（daemon，不会被杀）；

新实例 _job_active=False，认为空闲；

两个线程同时处理同一个视频，重复调用 LLM、重复写同一个输出文件。

MoviePilot 多 worker 部署时，不同进程更是各自为政。os.replace 保证不会写坏文件，但保证不了不重复烧钱。

修法：文件锁（fcntl.flock）按“目标目录/视频路径”加锁；锁文件放在插件数据目录；跨进程有效。stop_service 里 join 一个短超时，至少记录“旧任务未退出”。

P1-8　HTTP API 接受任意路径，存在越权读写风险

# plugins.v2/subtitlehunter/workflow.py:76-140
def api_list_subtitles(self, path: str = ""):
    target_paths = self._split_target_paths(path or self._target_path)
    ...
def api_ensure_chinese(self, payload=None):
    target_path = payload.get("path") or self._target_path
    ...
def api_extract_subtitles(self, payload=None):
    video_path = self._resolve_target_path(payload.get("path") or "")

path 完全没有限制：可以是 /etc、../../、符号链接指向的任意目录。/ensure 还会在目标目录写字幕文件。虽然 API 需要 MoviePilot 的 apikey，但：

多用户/多租户部署里，apikey 可能被共享；

一旦 apikey 泄露，攻击者可以枚举文件系统、写任意目录；

路径穿越是最基础的 Web 安全问题。

修法：维护允许根目录列表（target_path 配置的根 + 媒体库根）；Path.resolve() 后 is_relative_to(root)；拒绝符号链接逃逸；对 .. 显式拒绝；API 返回 400 而不是静默处理。

P1-9　__request_json 把 4xx/5xx 全部当成“无响应”

# plugins.v2/prowlarrextend/__init__.py:318-331
ret = RequestUtils(...).get_res(api_url)
if not ret:
    return None
if getattr(ret, "status_code", 200) >= 400:
    return None

requests.Response.__bool__ 在 status_code >= 400 时返回 False（实测 401/404/500 均为 False）。所以第二个 status_code >= 400 分支永远走不到：

401（Key 错）→ “Prowlarr 无响应”；

404（地址错）→ “Prowlarr 无响应”；

429（限流）→ “Prowlarr 无响应”；

500（Prowlarr 内部错）→ “Prowlarr 无响应”。

用户拿到的诊断信息是错的，排查方向也会错。

修法：先判 ret is None，再判 status_code；把 401/403/404/429/5xx 分别映射成明确的错误信息；不要在 __request_json 里吞掉状态码。

P1-10　test_connection 有副作用，会改写同步状态

# plugins.v2/prowlarrextend/__init__.py:255
indexers = self.get_indexers()

get_indexers() 不是只读：

# plugins.v2/prowlarrextend/__init__.py:333-342
def get_indexers(self):
    self._indexers_authoritative = False
    indexers = self.__get_indexers_from_config()
    if indexers is not None:
        self._indexers_authoritative = True
        return self.__apply_indexer_selection(indexers)
    ...

一个“测试连接”的 GET 接口，会重置 _indexers_authoritative、刷新 _indexer_catalog、改变多选过滤结果。并发时可能让正在进行的 sync_indexers 看到错误的 authoritative 状态，从而跳过/执行站点清理。

修法：/test 只做 GET /api/v1/system/status + GET /api/v1/indexer 的只读探测，返回数量和版本；不要调用 get_indexers()，不要碰任何实例状态。需要刷新就单独提供 /refresh。

P1-11　插件强行改写 SystemConfigKey.IndexerSites

# plugins.v2/prowlarrextend/__init__.py:840-861
selected_sites = self.systemconfig.get(SystemConfigKey.IndexerSites) or []
...
self.systemconfig.set(SystemConfigKey.IndexerSites, cleaned_sites + missing_ids)

这带来三个问题：

用户无法取消单个桥接站点的搜索。用户在 MoviePilot 设置里去掉一个站点，下次同步插件会把它加回来；唯一控制入口变成插件的 selected_indexers。

全局副作用。一个插件改写宿主的全局搜索范围，会触发 SiteUpdated、配置变更事件，可能和其他插件形成循环。

“空表示全部”的语义被破坏。如果 IndexerSites 为空表示“全部站点”，插件直接 return，行为又不一样。

修法：不要碰 IndexerSites。桥接范围由插件自己的 selected_indexers 决定；如果用户想在 MoviePilot 里按站点过滤，应该在插件结果里带上 site_name，让宿主 UI 去筛。

P1-12　假站点污染 Site 表，且无法通过健康检查

# plugins.v2/prowlarrextend/__init__.py:768-783
payload = {
    "name": indexer.get("name"),
    "domain": domain,                 # prowlarr-15.extend
    "url": f"https://{domain}/",     # 不存在的域名
    "is_active": True,
    ...
}

MoviePilot 的站点表不只有“搜索”一个用途：站点连通性检测、RSS、签到、用户数据、做种检查、下载器路径映射都可能遍历它。一个 https://prowlarr-15.extend/ 的站点：

DNS 不解析；

健康检查必然失败；

站点列表里出现一堆用户不认识的“站点”；

每次同步都发 SiteUpdated 事件。

插件用 search.paths=[] 让系统蜘蛛“尽早放弃”，但这只是让搜索跳过，其他子系统不一定买账。

修法：v3 架构下彻底删除假站点；如果为了 v2 兼容保留，至少 is_active=False、note.managed_by 标记、并在健康检查/统计里排除。

4.2 虚拟站点是“架构谎言”

这个插件最核心的设计是：把每个 Prowlarr 索引器伪装成 MoviePilot 的一个站点。为了让这个谎言成立，代码里出现了一整套补丁：

prowlarr_domain_suffix = "extend"、prowlarr-15.extend 假域名；

search.paths=[] 让系统蜘蛛放弃；

_is_managed_site() 按 domain/name/parser 三重判断；

__get_indexer_id() 从 domain、id、url 四种来源猜 ID；

残留站点跳过、catalog 清空、legacy domain 清理；

SiteUpdated 事件、SystemConfigKey.IndexerSites 同步。

这些补丁本身写得很认真，但它们在解决一个本来不该存在的问题。正确的边界是：

Prowlarr 是一个外部搜索提供者；MoviePilot 的 plugin source 是官方扩展点。把 Prowlarr 建模成“搜索提供者”，而不是“站点”。

一旦改成 plugin source：

不需要假域名；

不需要 SitesHelper.add_indexer；

不需要 Site CRUD；

不需要 IndexerSites；

不需要 __get_indexer_id 猜谜；

不需要残留站点清理；

v3 兼容问题自然消失。

这不是“重构”，是删掉一半代码。

4.3 Mixin 不是模块化，是分布式上帝类

SubtitleHunter 由 5 个 mixin + _PluginBase 组成：

class SubtitleHunter(
    MediaOpsMixin,
    TranslateOpsMixin,
    WorkflowMixin,
    RuntimeOpsMixin,
    UIMixin,
    _PluginBase,
):

它们共享 self._runtime、self._job_active、self._cancel_event、self._api_*、self._target_path 等几十个属性。任何 mixin 都可以读写任何状态，没有接口、没有边界、没有依赖声明。

这不是“拆开了上帝类”，而是把上帝类拆成 5 个互相偷看私有状态的类。MRO 还成了 bug 来源：v2.18 的版本记录就是“修复 mixin MRO，确保 get_form/get_page/stop_service 可加载”。用继承顺序来保证方法解析，是脆弱的。

修法：组合优于继承。SubtitleHunter 只持有 JobRunner、Translator、MediaRepository、Notifier；每个组件通过构造函数拿依赖，通过 dataclass 传状态。

4.4 状态机是字符串

"未运行" / "运行中" / "完成" / "部分失败" / "已取消" / "已跳过" / "配置错误" / "失败" / "已有中文" / "已生成中文" 散落在 workflow.py、runtime_ops.py、ui.py、codes.py。

拼错一个字符串，UI 颜色就错；

新增状态要改 4 个文件；

map_error_message 用中文子串匹配错误类型（"取消" in message、"AI" in text），换个措辞就失效；

FailureCode 已经有 Enum，但没有贯穿到状态机。

修法：JobStatus(str, Enum) + CueStatus(str, Enum) + FailureCode；所有赋值/比较走 Enum；UI 用映射表；错误分类在抛出点决定，不要靠事后字符串猜。

4.5 配置默认值有三份，迁移是临时的

默认值同时存在于：

init_plugin（__init__.py:50-79）

_current_config（__init__.py:212-242）

ui.get_form 的返回值（ui.py:373，实际调用 _current_config）

加一个字段要改 3 处；漏一处就出现“表单显示 A、运行时用 B”。

迁移逻辑也是临时的：

# subtitlehunter/__init__.py:101-104
self._api_retries = self._safe_int(config.get("api_retries"), 10, 0, 100)
if self._api_retries < 10:
    self._api_retries = 10
    config_changed = True

用户故意设 3（本地小模型、无 rate limit）也会被强制改成 10。表单还把 api_retries 隐藏了，用户无法改回。

修法：@dataclass(frozen=True) PluginConfig + from_raw() + to_dict()；一份默认值；版本化迁移（config_version）；迁移只做一次，不做“每次加载都强制”。

4.6 get_form 是手写 JSON 的泥石流

ProwlarrExtend.get_form 212 行，SubtitleHunter.get_form 367 行，全是嵌套 dict：

{'component': 'VRow', 'content': [
    {'component': 'VCol', 'props': {'cols': 12, 'md': 4}, 'content': [
        {'component': 'VSwitch', 'props': {'model': 'enabled', 'label': '启用插件'}}
    ]}
]}

没有 builder、没有 schema、没有布局复用。改一个字段要数括号；测试只能靠 find_select 递归查找（test_prowlarrextend.py:568-589）。

修法：ui/builders.py：row(*cols)、col(md=4, *children)、switch(model, label)、text_field(...)。同样的 dict 输出，代码量降到 1/4，可读性和可测试性都上来。

4.7 异常处理：31 处 blind except，另有 3 处静默 pass/continue

ruff --select BLE001 报了 31 处 except Exception，另有 3 处 S110/S112（try-except-pass / try-except-continue）。有些是合理的边界兜底（插件不能崩宿主），但很多是把“可诊断的错误”变成“静默降级”：

__request_json 吞掉 JSON 解析错误；

_load_runtime_state 吞掉状态损坏；

_save_runtime_state 吞掉写盘错误；

_cleanup_translation_cache 吞掉 stat/unlink 错误；

_translate_stage 对任何异常重试 11 次。

修法：定义 ProwlarrError / TranslationError 层级；只在边界（插件入口、任务线程）兜底；兜底时记录 type(e).__name__ + 上下文；不要用 except Exception: pass。

4.8 可观测性：日志有，但没有关联 ID

日志都是 【ProwlarrExtend】... / 【SubtitleHunter】...，没有 job_id、video_id、batch_id。多目标/多批次并发时，日志交错，无法回答“这个视频的翻译为什么失败”。

SubtitleHunter 有 stage_timings，但只存在内存/状态 JSON 里，没有结构化输出；ProwlarrExtend 没有阶段耗时。

修法：每个任务生成 job_id，日志统一 job_id=... video=... stage=...；关键阶段记录耗时、重试次数、token 用量；状态 JSON 加 schema_version。

4.9 Prowlarr API Key 可能进入日志/下载历史

这不是插件的错，但插件是链路的一环。Prowlarr 的 DownloadMappingService 把下载链接构造成：

// Prowlarr src/NzbDrone.Core/Download/DownloadMappingService.cs:40
var proxyLink = $"{serverUrl}{urlBase}/{indexerId}/download?apikey={_configFileProvider.ApiKey}&link={encodedLink}&file={urlEncodedFile}";

也就是说，TorrentInfo.enclosure 里天然带着 Prowlarr 的 API Key。插件把它原样放进 TorrentInfo，MoviePilot 可能把它写进下载历史、日志、通知或错误信息。

修法：插件不要在日志里打印完整 enclosure；错误信息里把 apikey=... 替换成 apikey=***；如果 MoviePilot 的下载历史会持久化 enclosure，在 README 里提醒用户这是 Prowlarr 的设计，并建议使用独立的 Prowlarr API Key / 反代白名单。

test_search_timeout_survives_form_defaults（test_prowlarrextend.py:278-288）：断言 defaults["search_timeout"] == 30，而插件配置是 60；这其实在测试“表单默认值不是当前值”，语义容易误导。

test_eta_does_not_multiply_total_chars_by_video_count（:220-230）：把“10 个视频和 1 个视频耗时相同”固化成期望；如果 total_chars 的语义变成“每个视频的字幕量”，这个测试会阻止正确修复。

5.5 CI 不可复现

CI 只有 27 行：

- run: python -m pip install pytest ruff
- run: ruff check plugins.v2/ tests/
- run: python -m pytest tests/ -q

没有 pyproject.toml、没有 ruff.toml、没有 pin 版本、没有 matrix、没有 coverage、没有类型检查。

同一份代码：

2026-08 的 ruff（默认规则较窄）→ 绿；

2026-10 的 ruff 0.17.1（默认规则大幅扩展）→ 380 条（UP006 214、UP045 52、UP035 37、BLE001 31、UP009 19…）；

显式 --select E4,E7,E9,F → 0 条。

也就是说：CI 的绿灯依赖于“当时安装到的 ruff 版本”，不是代码质量。 今天重新跑 CI 会红，但红的不是 bug，是规则集变了；反过来，真正该管的 BLE001（blind except）在 CI 里根本不开。

修法：pyproject.toml 固定 target-version=py311、line-length=120、[tool.ruff.lint] select = ["E","F","I","B","UP","SIM","BLE","S"]；CI pin ruff==0.17.1、pytest==8.x；加 ruff format --check；加 pytest --cov（先设 60%，逐步提高）；加 Python 3.11/3.12/3.13 matrix。

5.6 发布流程：没有 release，等于没有回滚

README 说“重启容器时会从 GitHub 拉最新代码”。这意味着：

main 的每个 commit 都是生产版本；

没有 tag、没有 release notes、没有 rollback；

一个坏 commit 会让所有用户同时坏；

用户无法说“我锁定在 v2.12”。

对一个公开插件，这是供应链风险，不是“方便”。

修法：main 保持稳定；开发在 dev；每次发布打 tag（v3.0.0）；package.v2.json 的 version 与 tag 对齐；提供 COMPATIBILITY.md（插件版本 × MoviePilot 版本 × 测试日期）；README 给出“锁定版本”的方法。

6. 文档的可信度问题

文档多是优点，但有几处会误导维护者：

PLAN.md 的目标 v2.14.0 是真实版本（2026-06-30），插件也确实按它写的，这一点没问题。问题是：v2.14.0 之后宿主进入了 v3（v3.0.0 于 2026-09-12），而 README 仍然只写“MoviePilot V2”，没有兼容矩阵，也没有“v3 不支持”的提示。目标版本选对了，但生命周期没跟上。

MAINTENANCE.md 的风险表把 SitesHelper.add_indexer 标为“低风险”，理由是“官方 customindexer 插件也在用”。在 v2.14.0 时代这是合理的；但 v3 的公开接口里已经没有它，风险表没有更新。风险表不是一次性文档，宿主大版本升级时必须重写。

README 说“复用 MoviePilot 系统智能助手配置”。实际读的是 settings.LLM_*，且只支持 OpenAI 兼容 /chat/completions；v3 的 runtime setting 可能读不到，Gemini/Claude 原生会失败。

README 说“失败有界……不会永久占住后台任务”。技术上没错，但 11 次重试 × 最长 5 分钟 × 3 阶段，单批最坏 75 分钟；这不是用户理解的“有界”。

README 说“代理禁用修复”。proxies={"http": None, "https": None} 依赖 requests 的 None 覆盖语义，建议改成 Session.trust_env = False，更明确。

版本历史顺序混乱：README 的 SubtitleHunter 历史从 v2.19 跳到 v2.4，再 v2.5…v2.18；读者无法判断时间线。

CLAUDE.md 说“SitesHelper 是 .so 编译文件，无法直接阅读源码，只能通过官方插件用法推断接口”。这句话本身就承认了最大的风险：核心接口靠推断。正确做法是查 .pyi / 官方源码 / 契约测试，而不是“推断”。

7. 重构方案

7.1 目标与原则

只使用宿主公开、稳定的扩展点：get_module() 的 plugin source、get_service()、get_api()、get_form()/get_page()；不碰 SitesHelper.add_indexer、不写 Site 表、不改全局 IndexerSites。

v3-first，v2 兼容可选：先保证 v3.1.9 可用；v2 用能力检测做降级，不把双路径写死。

不可变快照 + 单飞刷新：索引器列表是一个 immutable snapshot；刷新是 single-flight；搜索只读快照，不加锁。

组合优于继承：删掉 mixin，改成 JobRunner / Translator / MediaRepository / Notifier 组合。

错误分类，不吞异常：边界兜底，内部抛类型化异常；重试只针对可重试错误。

测试契约，不测试替身：真实宿主（pinned）+ 假 Prowlarr + 黄金字幕 + 属性测试。

def search_torrents(self, site, keyword, mtype=None, page=0):
    if not keyword:
        return []
    indexers = self._registry.snapshot()
    if site:
        indexer_id = self._resolve_indexer_id(site)
        if not indexer_id:
            return []
        indexers = tuple(i for i in indexers if i.id == indexer_id)
    if not indexers:
        return []
    return self._search_service.search(indexers, keyword, mtype, page)

关键修复点：

重试分类：Retryable = RateLimited | ServerError | Timeout | ConnectionError；AuthError | BadRequest | ContentPolicy 立即失败。

批次二分：MissingIndices / OutputTruncated → split(batch) 递归，直到 1 条；单条仍失败才标记失败。

token 预算：按模型上下文估算输入+输出 token；max_tokens 显式设置；超过预算先拆批。

样式保留：SubtitleCue 增加 style_prefix/style_suffix；翻译只处理 plain_text；渲染时拼回。

编码检测：charset-normalizer，回退 utf-8-sig → utf-16 → gb18030 → cp1252；失败明确报错。

forced 检测：只匹配语言标签后的 forced/foreign 后缀；删除 only/signs。

语言映射：pycountry 或完整 639-2/639-1 表；输出 ja/fr/de/es 等 Jellyfin 友好标签。

质量门：覆盖率 0.9 + 逐条检查 + 长英文行检测。

季包：按目录 debounce 30–60 秒，pending 集合合并；或队列消费。

跨进程锁：fcntl.flock 按目标目录；stop_service join 短超时。

路径安全：允许根列表 + resolve() + is_relative_to。

9. 结论

这套代码最值得肯定的地方，是作者知道怎么把逻辑拆成纯函数、怎么写原子文件、怎么做缓存和状态。这些是真正的工程能力。

但它也暴露了一个更根本的问题：把“能跑”当成了“架构正确”。虚拟站点在 v2 上确实能跑，于是所有补丁都围绕这个假设生长；测试用替身把宿主 API 固定住，于是绿灯掩盖了契约漂移；文档把“推断出来的接口”写成了“稳定接口”，于是风险表全是绿色。

v3 的到来只是把这个假设戳破了。即使没有 v3，这套设计也会在以下场景出问题：

用户想取消某个桥接站点的搜索；

用户升级 MoviePilot 后站点表出现一堆假域名；

季包入库只处理第一集；

模型返回被截断，插件重试 11 次后卡死；

字幕是 GBK，翻译出来是乱码；

ASS 字幕翻译后所有定位/样式丢失。

所以，最严苛的评价不是“代码写得丑”，而是：

这是一个“在特定版本上能跑”的插件，不是一个“可以长期维护”的插件。它的聪明用在了绕过宿主模型上，而不是顺应宿主模型上。

最后一句

先把 ProwlarrExtend 从“假站点”改成“搜索提供者”。这不是重构，是把插件从宿主的敌人变成宿主的公民。做完这一步，v3 兼容、Site 表污染、IndexerSites 副作用、假域名、ID 猜谜、残留站点清理，会一起消失。
